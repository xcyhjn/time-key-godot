# Unity 3D 迁移可行性与难度评估

> 状态：门禁通过（CONDITIONAL GO）
> 负责人：主智能体
> 最后验证日期：2026-07-31
> 证据来源：Godot 实跑截图/日志、源代码符号、卡牌与存档样本、本机 Unity 包目录

## 结论

**决策：CONDITIONAL GO，总体难度 4/5（高）。**

迁移在技术上可行。核心规则规模可控，卡牌 JSON 只有 7 份，时间轴和六边形坐标已有相对清晰的规则模块；Unity 6000.4.10f1、URP 17.4.0、uGUI 2.0.0 和 Test Framework 1.6.0 均已在本机安装。高难点不是 C# 语法转换，而是还原隐式场景/信号生命周期、替换 card-framework、明确当前实现缺口，以及在不牺牲信息密度的前提下把地图与战场重建为 3D。

条件不阻塞首个切片：

- 未确认的图片、音频、中文字体授权：首切片只用 Unity 原生几何体、默认字体和程序化颜色，不复制来源不明素材。
- 是否兼容 Godot `save_0.cfg`：首切片只冻结版本化 Unity DTO 与导入器边界，不承诺旧档转换。
- Dialogic 授权和教程完成度：教程不在首切片范围。

## 难度评分

| 维度 | 难度 | 置信度 | 证据 | 缓解方案 |
| --- | ---: | ---: | --- | --- |
| 玩法规则 | 4 | 高 | 时间轴已模块化，但敌人意图 action 的命令解析当前为空，建筑行为在整条时间轴后统一执行 | 先锁定可观察顺序；纯 C# 规则层用 golden fixture 测试 |
| 场景与生命周期 | 4 | 高 | composition root 分散在 `out_scene_map_exp.gd`、`in_scene.gd`、`hex_map.gd`，切场用 instantiate/add_child/current_scene | Unity 用显式 bootstrap、场景上下文 DTO 和 service 生命周期 |
| 数据与存档 | 4 | 高 | JSON、Resource、场景导出字段、Vector2i 字典键和无版本 CFG 并存；时间币等状态未真正落盘 | 版本化 DTO；静态配置与运行态分离；旧档适配器独立 |
| 第三方插件 | 5 | 高 | card-framework 贯穿卡牌、手牌、牌堆、奖励；Dialogic 功能面小但 vendored 根授权不清 | card-framework 按行为重写；Dialogic 延后并先完成授权核对 |
| 2D 到 3D | 4 | 中高 | 地图/战场高度、建筑、目标反馈需重做；缺少模型、动画、材质资产 | 白盒→过渡资产→目标资产三层；首切片程序化几何 |
| Shader/VFX | 3 | 高 | 24 个非插件 shader 全是 `canvas_item`，17 个有明确引用 | 先保留语义清单；当前切片只用 URP Lit/Unlit 材质 |
| UI/输入 | 4 | 高 | 卡牌交互是“选卡→选世界目标→点时间轴”，并含 Q/E 旋转、tooltip、固定 1920×1080 偏移 | uGUI 单一栈；屏幕空间时间轴；双视口 PlayMode/截图验收 |
| 测试性 | 5 | 高 | 当前无正式测试套件，随机生成和场景状态较多 | 固定 seed、纯规则层、结构化快照、EditMode+PlayMode+batchmode |
| 性能与构建 | 3 | 中 | 目标平台未冻结；资产约 40 MB；开发机内存预检偏低 | 首切片以 Windows 桌面为开发基线；建立帧时和内存快照而非发布承诺 |
| 团队并行度 | 3 | 高 | Domain、工程基座、3D 表现可拆，但共享 schema/坐标/场景契约必须先冻结 | 所有权互斥；共享文档只由主智能体更新；波次集成 |

## 工作量区间与假设

**推断**：在 1 名熟悉 Unity 的高级工程师全职、复用现有 2D 内容、白盒优先、Windows 桌面为第一验证平台的假设下：

- 首个可验证垂直切片：约 3–6 工程日。
- 核心战斗与局外闭环达到功能等价：约 8–14 工程周。
- 包含教程、奖励页、存档迁移、主要 VFX/音频与发布加固：总计约 16–28 工程周。

这不是承诺工期。若要求完整旧档兼容、全部最终 3D 资产或多平台同发，区间需要重新评估。

## 关键路径

1. Godot 行为基线与数据/顺序契约。
2. Unity 工程基座、包锁、测试与截图 harness。
3. 纯 C# 卡牌/形状/时间轴/效果/意图模型。
4. 固定种子 3D 六边形战场和屏幕空间卡牌/时间轴。
5. 局外地图、奖励返回、跨场景状态和版本化存档。
6. 教程/音频/VFX/资产授权与发布。

## 三个最大未知数

1. 是否必须导入现有 Godot CFG 存档。
2. 图片、音频和 ARK Pixel 中文字体是否拥有 Unity 发布所需授权。
3. 敌人意图应按时间轴列直接执行，还是保持当前“只占位展示、回合末建筑统一行动”的可观察实现。

## 三个主要失败模式

1. 逐行翻译节点/单例，导致 Unity 生命周期与状态所有权再次隐式耦合。
2. 先批量搬素材和页面，长期没有可运行的规则—3D—测试闭环。
3. 把设计文档中的意图当成当前行为，悄悄修正 Godot 已存在的规则缺口，造成玩法漂移。

## 迁移策略比较

| 策略 | 优点 | 主要风险 | 结论 |
| --- | --- | --- | --- |
| 一次性全量重写 | 最终目录一次成型 | 长期不可运行、难定位漂移、回滚面大 | 不采用 |
| 按系统横向迁移 | 便于专业分工 | “数据都迁了但游戏不能玩”，跨系统契约迟到 | 只作为纵向切片内部子任务 |
| 最小可玩闭环纵向切片 | 每批都能运行、测试、截图和对照 | 需要先冻结薄契约 | **采用** |

## 首个切片冻结范围

**输入**：真实 `card_data/lighting.json`、固定 3×12 时间轴、一个固定目标（10 HP）、一个固定敌人意图、固定六边形白盒布局。

**输出**：Unity 可加载场景显示 3D 六边形战场和屏幕空间时间轴；雷击卡可合法放置；结算顺序产生结构化日志；目标从 10 HP 变 0；敌人意图按冻结契约可观察；截图覆盖 1920×1080 和 1280×720。

**非目标**：完整局外流程、教程、奖励页、所有卡、最终资产、全部 shader、旧档导入、多平台发布。

**验收**：EditMode、PlayMode、batchmode 启动全部通过；两视口截图无裁切/空白/不可读主要信息；parity matrix 有逐项结论；Git 检查点不包含用户原有脏文件。
